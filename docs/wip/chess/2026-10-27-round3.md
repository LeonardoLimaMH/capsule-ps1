# CHESS: argumento omitido e consulta ao Ghidra

## Candidato byte-matching

`func_800C9484` ocupa 0x58 bytes. O primeiro parâmetro não é lido, mas precisa
existir para posicionar o segundo em `$a1`. A heurística `arggaps` recuperou
esse detalhe na passagem completa pelas 768 funções então pendentes.

A expressão C abaixo também produz o mesmo código com GCC 2.8.1:

```c
return (column + ((*D_80069BBE + 128) % 4096) / 256) % 16;
```

Ela mantém a divisão e o resto assinados, inclusive para valores negativos;
substituir `% 4096` por `& 4095` não preservaria esse comportamento. O primeiro
rascunho tinha shifts e ajustes de sinal explícitos. Comparar também os
operadores C de alto nível permite simplificar o código sem perder o casamento.

A função foi colocada na unidade GCC 2.8.1 de `func_800C942C`; a unidade seguinte
passa a começar em `func_800C94DC`, preservando seu GCC 2.7.2. O comentário
`rand-u16` exercita o global de fase com zero, limites de divisão e halfwords
que representam valores assinados negativos. O C equivalente duplicado é
removido quando a função é integrada.

Resultado da integração: **100 / 867 funções do jogo**, **7.268 / 421.956 bytes
(1,72%)** em C byte-exact; continuam pendentes 767 funções. O CHESS reconstruído
manteve SHA-1 `a6a63cc46a633968573c23b5681bb178070dba25`. Os cinco testes de
rebuild passaram na área isolada, e `func_800C9484` e `func_800C942C` passaram
em 200 execuções diferenciais estritas cada, com o global de fase variando.

A função vizinha `func_800C94DC` também foi investigada com operadores de resto
e divisão. A ordem de instruções ainda difere; ela continua em assembly.

## Ghidra disponível

Confirmados Ghidra 12.1.4, extensão GhidraMCP 7.0.0 e API HTTP local em 8089.
O projeto existente é `../Ghidra/Ghidra.gpr`, com os cinco programas em
`/ygo_elf/`. A conexão estava desligada e foi iniciada durante esta rodada.
`tools/ghidra.py` já fornece acesso à mesma API sem precisar de uma ferramenta
MCP registrada no cliente.

Consultas ao vivo realizadas para `func_800C47B8`, `func_800C61F4` e
`func_800C9B78`. Nenhum tipo ou protótipo foi alterado no projeto compartilhado.

Em `func_800C47B8`, o pseudo-C fragmenta uma cópia local de dez bytes em campos
e operações de bits. O assembly mostra duas cargas/stores de palavras não
alinhadas e dois bytes. Uma struct contendo `u8 values[10]`, inicializada a
partir de `D_800988C8`, reproduz esse padrão de cópia. O primeiro rascunho com
essa struct compila, mas ainda difere na alocação, ordem e epílogo: **não é um
novo byte-exact e não deve aumentar o progresso**. O callback `func_800C61F4`
ajuda a interpretar os campos do objeto retornado, sem tornar os tipos
inferidos uma prova de equivalência.

Em `func_800C9B78`, o Ghidra ainda representa helpers soft-float como pares de
inteiros. Recuperar os protótipos desses helpers e conferir o uso do retorno
nos chamadores continua necessário antes de promover o C.
